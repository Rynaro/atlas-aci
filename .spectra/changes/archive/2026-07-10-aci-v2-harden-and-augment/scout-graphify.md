## Claim 1 — Edge confidence tagging

**VERIFIED, with a critical nuance the dossier didn't ask for explicitly.**

- Enum: `graphify/validate.py:5` `VALID_CONFIDENCES = {"EXTRACTED", "INFERRED", "AMBIGUOUS"}`, enforced in `validate_extraction()` (`graphify/validate.py:68-72`).
- Schema doc: `ARCHITECTURE.md:43,50-56` — matches the enum exactly.
- **Producers, traced precisely:**
  - `EXTRACTED` / `INFERRED` in the **deterministic AST path** (`graphify/extract.py`): set via a `type_qualified` boolean, no LLM involved. E.g. `graphify/extract.py:2374-2375`, `2488-2489`, `2598-2599` (Swift/Kotlin/PHP-style member-call resolvers): `"confidence": "EXTRACTED" if type_qualified else "INFERRED"`. Comment at `extract.py:2339`: "Determine the receiver's type and the resulting confidence." The cross-file C++ resolver (`_resolve_cpp_member_calls`, ~`extract.py:3330-3480`) and the shared cross-file member-call pass (`extract.py:2000-2070`) apply the identical rule: a type name explicitly in source (`Type.method()`, `this->bar()`, `Foo::bar()`) → `EXTRACTED`; a type inferred from a per-file local variable-type table → `INFERRED`. Always gated by a "god-node guard" (`len(type_defs) != 1` → bail, no edge at all) — i.e. it never guesses under ambiguity, it just drops the edge.
  - `AMBIGUOUS` is **never emitted by any AST/deterministic extractor**. Confirmed by exhaustive grep: `grep -n AMBIGUOUS graphify/extract.py graphify/extractors/*.py` → zero matches. The only place `"AMBIGUOUS"` is written as an edge value is inside the **LLM semantic-extraction prompt** at `graphify/llm.py:416` ("AMBIGUOUS: uncertain — flag for review, do not omit") and `llm.py:437,445` — i.e. the LLM decides for itself, per free-form instructions, which edges among doc/paper/image content deserve that tag. Every other reference to `AMBIGUOUS` (`analyze.py`, `report.py`, `export.py`, `wiki.py`, `serve.py`, `callflow_html.py`) is a **consumer**, not a producer.
  - So: `INFERRED` is dual-sourced (deterministic second-pass on code, LLM judgment on docs/papers/images); `AMBIGUOUS` is LLM-only.
- **Schema enforcement is soft, not hard**, contrary to `ARCHITECTURE.md:48`'s own claim ("`validate.py` enforces this schema before `build_graph()` consumes it"): the only production call site is `graphify/build.py:380` (`errors = validate_extraction(extraction)`), and errors are just printed to stderr as a warning (`build.py:383-384`) — build continues regardless. The function that actually raises, `assert_valid()` (`validate.py:90-95`), has **zero production callers** (`grep -rn assert_valid graphify/*.py` → only its own definition); it's exercised solely by `tests/test_validate.py:82-87`. Verdict on the "enforces" framing: **PARTIAL** (validated-and-warned, not validated-and-blocked).

## Claim 3 — Incremental indexing

**VERIFIED** (mechanism), **change-detection key = mtime + MD5 content hash, not git SHA**.

- CLI surface: `graphify update [path] [--force] [--no-cluster]` (`graphify/cli.py:1218-1272`), explicitly "no LLM needed" (`cli.py:1252`), plus a post-commit **and** post-checkout git hook installed via `graphify hook install` (`graphify/hooks.py:483-517`, `install()`).
- Change-detection key: **file mtime, verified by MD5 on mismatch** — NOT a git SHA. `graphify/detect.py:1472-1570` (`detect_incremental`): manifest entries are `{"mtime": ..., "ast_hash": ..., "semantic_hash": ...}` (schema doc at `detect.py:1483-1496`). Fast path: mtime unchanged + hash present → unchanged, no I/O beyond `os.stat` (`detect.py:1524,1548-1552`). Slow path: mtime bumped → `_md5_file(Path(f)) != stored_hash` (`detect.py:1550`) before triggering re-extraction. Two independent hash fields let `graphify update` (AST-only, `kind="ast"`) and `graphify extract` (semantic, `kind="semantic"`) each track their own staleness independently (`detect.py:1478-1489`).
- **Deletions**: `detect_incremental` computes `deleted_files = [f for f in manifest if f not in current_files]` (`detect.py:1562-1563`).
- **Stale edges** (the hard part) are handled in `graphify/watch.py`'s merge routine `_merge_...` (function signature at `watch.py:369-381`, docstring: "Merge fresh extraction with preserved graph entries and evict stale sources"). It computes `node_evicted_source_identities`/`edge_evicted_source_identities` from `deleted_source_identities` plus rebuilt-file identities (`watch.py:409-414`), reconciles every existing node's `source_file` against the currently-watched corpus even for files not explicitly listed as changed (rename-safety, `watch.py:416-433`), then filters `preserved_nodes`/`preserved_edges` to drop anything whose source was evicted (`watch.py:438-467`). `graphify/build.py` separately handles "ghost" ↔ "AST-canonical" node reconciliation (`build.py:392,435-506`) for the LLM-semantic-vs-AST duplicate-node problem, unrelated to deletion per se.
- `--code-only` flag (`cli.py:1978-1979,2102-2113`) skips the semantic (doc/paper/image) pass entirely so a mixed repo without an LLM key still indexes cleanly — pure local AST path.

# Deliverable 3 — Transferable design, and what to avoid

## Structurally right (candidates worth studying further)

1. **Version-namespaced AST cache with auto-sweep.** `graphify/cache.py:16-24`: the per-file extraction cache lives at `cache/ast/v{package_version}/`, and stale sibling-version directories are swept on first use (`_cleanup_stale_ast_entries`, `cache.py:35+`). This solves the exact "extractor bugfix ships, but old cache entries silently keep serving wrong output" problem a hardened long-lived tool will hit. Explicitly contrasted with the semantic (LLM) cache, which is deliberately **left unversioned** to avoid re-billing LLM extraction on every point release (`cache.py:20-24`) — a considered, documented tradeoff rather than an oversight.
2. **Per-file error isolation, not batch-fatal.** `_safe_extract()` (`extract.py:156-167`) wraps every single-file extractor call, catching `RecursionError` and generic `Exception`, returning `{"nodes": [], "edges": [], "error": "..."}` instead of crashing; combined with `_raise_recursion_limit()` (`extract.py:142,151-153`, cap 10,000) and `ProcessPoolExecutor`-based parallel extraction (`extract.py:3937+`, `_extract_parallel`) so a genuinely fatal per-file crash (e.g. a segfault-prone grammar) only takes down one worker, not the run, with a documented fallback to sequential extraction on `BrokenProcessPool` (`extract.py:3944-3949`).
3. **God-node guard as a recurring correctness primitive.** The same pattern — "resolve to a type/target only if there is exactly ONE candidate definition, otherwise skip the edge entirely rather than guess" — appears independently in the Swift/PHP/C++/C#/Ruby cross-file resolvers (`extract.py:2073` region comment "len != 1 is the god-node guard", `extract.py:3352,3372`, `ruby_resolution.py:118-121`). This is a disciplined, deterministic precision/recall tradeoff (favor precision, drop ambiguous edges) that's directly transferable to any zero-LLM resolver atlas-aci builds.
4. **Fixture-driven, per-language regression tests at real scale.** `tests/test_languages.py` is 2,947 lines with 79 fixture files under `tests/fixtures/`, plus dedicated `tests/test_cross_language_call_resolution.py` and `tests/test_language_resolvers.py`. Total test volume (43,540 lines) is roughly on par with source volume (47,161 lines) — a real 1:1-ish test investment, not a token gesture.
5. **Deterministic identity re-keying between extractor generations.** `build.py:385-394` re-derives non-AST node IDs from `source_file` at merge time specifically so a stale cached fragment (e.g. an old semantic-cache entry with an outdated ID scheme) physically reconciles with the current AST node instead of spawning a duplicate "ghost" node — with an explicit ghost-detection/remap pass right after (`build.py:435-506`, `_ghost_remap`).
6. **Hard resource caps as a first line of defense**, not just docs: `GRAPHIFY_MAX_GRAPH_BYTES` (default 512 MiB, `README.md:519`), merge-driver's independent 50 MB / 100k-node cap (`cli.py:1362-1372,1384-1390`), `_FILE_CHAR_CAP` truncation before LLM calls (`llm.py:27`). Every one of these fails loudly (raises / exits 1) rather than degrading silently.
7. **Windows/PowerShell as a first-class constraint**, not an afterthought — e.g. `cluster.py:11-19` explicitly suppresses graspologic's ANSI output because it corrupts the PowerShell 5.1 scroll buffer; `hooks.py`'s `_PYTHON_DETECT` shell fragment (`hooks.py:15-80`) has multiple probes specifically for uv-tool/pipx isolated venvs and Windows `.exe` shebang edge cases. Worth noting given atlas-aci presumably also has to survive varied host environments.

## What's wrong / paid dearly for — avoid

1. **Documentation/CHANGELOG drift from shipped code.** The merge-driver auto-wiring claim (Claim 7) is stated confidently in both the README and a specific CHANGELOG entry, but is absent from the actual `hooks.py` at HEAD. In a 47k-line, apparently AI-heavily-authored codebase (commit message in this very HEAD commit is `Co-Authored-By: Claude Opus 4.8`), this is a concrete, findable instance of a claimed feature that isn't there — a cautionary data point for any tool (including one built the same way) about verifying documentation against code rather than trusting either in isolation.
2. **Extreme dispatch-table / dead-weight sprawl.** `_DISPATCH` alone has 92 suffix entries into 46 extractor functions, several with narrow/overlapping scope (5 separate DreamMaker sub-formats: `.dm/.dme/.dmi/.dmm/.dmf`, each its own extractor; Pascal has 4 sibling extractors — `extract_pascal`, `extract_delphi_form`, `extract_lazarus_form`, `extract_lazarus_package`). This is the cost of "support everything" breadth: `extract.py` is 4,754 lines and imports ~90 named helper symbols from `extractors/engine.py` in one line (`extract.py:134`). For atlas-aci's stated zero-LLM, mechanically-bounded thesis, this suggests: pick a narrow, high-value language set and resist the urge to chase exhaustive coverage — graphify's breadth is clearly its biggest maintenance liability (visible directly in file size and CHANGELOG volume: 260 KB / many hundreds of entries).
3. **Optional-dependency version gating as a silent capability cliff.** Leiden literally cannot run on Python 3.13+ (`graspologic; python_version < '3.13'`) — a user on a newer interpreter silently gets Louvain with no warning surfaced in the code path I read (worth double-checking at runtime, but `cluster.py`'s `_partition()` only catches `ImportError`, so a 3.13 user just silently falls through every time). If atlas-aci ever makes a similar "richer algorithm, optional dependency" choice, surface the fallback explicitly rather than silently.
4. **Self-referential "confidence" scoring is close to double bookkeeping.** Several edges carry both a categorical `confidence` (`EXTRACTED`/`INFERRED`) *and* a numeric `confidence_score` (e.g. `1.0`/`0.8`, `extract.py:2375,2489,2599`) that is always a fixed constant per category, not independently computed — i.e. it's a second encoding of the same three-way decision, not additional information. If atlas-aci wants a confidence signal, a single enum (or a single float with documented enum-equivalent thresholds) avoids this redundancy.
